# Architecture — text V1

The active project direction is English-only text input, output and text fine-tuning. Screenshot inference and image training are outside V1. The earlier screenshot CLI was replaced, and the screenshot evaluation directory was removed. Active training and evaluation data lives in `data/text/`.

## Current executable flow

```text
Streamlit text area / CLI --text or --file
  -> validate_input (nonempty plain text, at most 4,000 characters)
  -> shared build_messages prompt + local Ollama qwen3:4b
  -> require a completed structured response
  -> TextObservation, checked against the original input
  -> template summary, uncertainty and plain-text evidence
```

`analysis.py` calls only the loopback endpoint with proxy settings disabled. User input is JSON-encoded inside a user message; role markers and embedded instructions remain data. This separation reduces accidental interpretation as instructions but is not a prompt-injection guarantee. The model has no tools. It does not browse, follow user links or control a phone. The application does not write inputs to disk; external runtime logging configuration is outside this code.

`TextObservation` contains `category`, `signals` with exact evidence quotes, and `issues`. Unknown fields are rejected. Duplicate signals, Wi-Fi off plus connected, and connectivity signals in non-Wi-Fi categories are invalid. Any issue forces unknown and clears signals. Evidence must occur in the actual user input, rather than a model-generated transcription. Quote validation cannot detect all semantic mistakes, negation errors or invented interpretations. Summary and uncertainty fields are generated by application templates, excluded from model schema and training targets.

## Intended complete pipeline

```text
Text -> validated observations
     -> local document retrieval
     -> grounded explanation draft
     -> deterministic safety policy and action selection
     -> explanation, caution, next action, sources
     -> optional family handoff from the approved state
```

Future retrieval must translate `alert` into the existing `popup` catalog category and map supported signals and English descriptions to the English document vocabulary. The current retriever uses weighted keyword overlap on local files, not embeddings. The next stage must reject unsupported citations and explicitly handle no relevant source. Raw messages and training examples are never trusted RAG documents. Reference text is evidence, not authority to override safety rules.

Future action policy should use reviewed action IDs/templates, distinguish benign messages from requests for credentials/payment/remote access, and avoid treating every Wi-Fi problem as malicious. Network resets need consequence-aware handling. Family summaries should contain only approved observations/actions and exclude private credentials and unnecessary personal data.

## Text learning and evaluation

`data/text/{train,validation,test}.jsonl` contains 33 synthetic English examples covering 33 scenarios (19 train, 7 validation, 7 test). Each record has a correct observation, a wrong alternative, rationale, provenance, review state and optional local knowledge reference IDs. The labels received an automated consistency review on 2026-09-21; this is not human/domain review or an externally verified sender verdict.

`dataset.py` validates gold and intentionally rejected observations against their original input, rejects silently normalized labels and runtime-only gold issues, checks references and exact duplicate IDs/text, and prevents a scenario group from crossing splits. It does not automatically discover factual labeling errors or all semantic near-duplicates; manually review labels and scenario diversity. Existing scenario assignments are preserved after removing the Korean translations.

`--export artifacts/text-sft` exports only positive assistant completions for train and validation, using the same prompt builder as inference. It never exports test examples or rejected answers. This is supervised-data preparation, not a trainer. Future training should use completion-only loss, check tokenizer lengths before truncation, record model/tokenizer/adapter versions, and compare the same base model and runtime with/without the adapter.

Use train for weight updates, validation for prompt/hyperparameter/checkpoint choices, and a frozen test split for final reporting. The small authored test set is an initial check, not a real-world generalization claim. Add independently sourced, consented and de-identified unseen texts for stronger evaluation. Do not convert evaluated failures into training examples and still report them as held out.

Metrics should include category accuracy, per-signal precision/recall, evidence validity, abstention/coverage, false alarms on ordinary texts, missed concerning requests, unsafe-action rate, source relevance, and latency, broken out by category. Prevent test inputs from entering training or routine smoke tests. Actual training and full benchmark execution are not implemented yet.

## Selected PyTorch configuration

The development machine was checked on 2026-09-21: Apple M4 with 10 CPU cores,
16 GB unified memory, arm64 macOS, and 175 GiB free storage. PyTorch reports that
MPS is both built and available when run outside the restricted test sandbox.

The selected model is `Qwen/Qwen2.5-1.5B-Instruct` at immutable Hugging Face
revision `989aa7980e4cf806f80c7fef2b1adb7bc71aa306` (Apache-2.0). It has 1.54B
parameters and a 3,087,467,144-byte BF16 weights file. This is small enough for
LoRA training on this 16 GB Mac while retaining substantially more capacity than
the 0.6B alternative. A 4B model leaves too little working memory for reliable
PyTorch training and evaluation on this machine.

The implementation target is:

| Setting | Selected value |
| --- | --- |
| Runtime | PyTorch + Transformers + PEFT + Accelerate |
| Device | Apple MPS, with an explicit CPU fallback |
| Method | LoRA; no MLX, bitsandbytes, or QLoRA |
| LoRA targets | `q_proj`, `v_proj` |
| LoRA rank / alpha / dropout | 8 / 16 / 0.05 |
| Sequence length | 1,536 tokens; reject overlength training rows instead of truncating |
| Precision | FP16 frozen base weights; trainable adapter weights kept in FP32 |
| Microbatch / accumulation | 1 / 4 |
| Optimizer | AdamW, learning rate 2e-4, weight decay 0.01 |
| Schedule | 5 epochs, linear decay, 10% warmup, gradient clipping at 1.0 |
| Memory control | Gradient checkpointing; model cache disabled during training |
| Reproducibility | Seed 42; record package versions, revision, settings and metrics |
| Selection | Lowest validation loss; the test split stays unused until settings freeze |
| Inference | Greedy decoding, temperature 0, at most 256 new tokens |

Using the pinned tokenizer and the current shared prompt, complete examples are
1,139–1,212 tokens in train, 1,141–1,189 in validation, and 1,148–1,187 in test.
The 1,536-token limit therefore preserves every current prompt and target. Future
data preparation must run the same length check and fail on overflow. Training
loss must be masked so only assistant completion tokens update the adapter.

Baseline and adapter inference must use this same PyTorch runtime, tokenizer,
revision, prompt, decoding settings and output validation. This avoids comparing
an Ollama quantization with a differently configured trained model. The current
Ollama integration will be replaced rather than retained as a second production
runtime.

## Responsibilities

| File / directory | Responsibility |
| --- | --- |
| `app/app.py` | Text input, observations, explicit error display |
| `src/easy_tech_help/analysis.py` | Shared prompt, local text inference, CLI |
| `src/easy_tech_help/schemas.py` | Input and structured observation validation |
| `src/easy_tech_help/config.py` | Optional local text model setting |
| `src/easy_tech_help/dataset.py` | Dataset integrity and positive-only SFT export |
| `data/text/` | Authored train/validation/test examples and labeling guide |
| `src/easy_tech_help/retrieval.py` | Existing independent offline document search |
| `knowledge/` | FTC originals and labeled Apple summaries, separate from training |
| `tests/test_analysis_live.py` | Development smoke cases, not final evaluation |
| `artifacts/` | Ignored local generated data/weights, no committed model files |

Safety, RAG generation, handoff, a text training runner, adapter integration and a benchmark runner are the remaining modules. Existing local vision weights and MLX-VLM installations are not part of the text setup.
